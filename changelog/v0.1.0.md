# Guardrail Hub MCP Server v0.1.0

Release date: 2026-07-19

## Overview

The first release of the Guardrail Hub MCP Server — a Model Context Protocol (MCP) server built on FastAPI. The server provides a reusable execution platform for long-running tool operations: operation orchestration, worker management, pluggable persistence, notification infrastructure, and an extensible tool architecture. OWASP ZAP security scanning is the first capability built on this platform, exposed as a suite of MCP tools.

## Highlights

- A generic, tool-agnostic execution platform: operations are queued, dispatched to a self-registering worker pool, tracked through explicit lifecycle states, and reported to notification channels.
- Five OWASP ZAP scanning tools covering single endpoints, authenticated multi-step scenarios, whole application suites, and website scans.
- Aggregated suite reporting in Markdown, JSON, and SARIF 2.1.0.
- Real-time operation progress delivered to Slack as in-place message updates.
- Horizontal scaling with `docker compose up --scale zap=N` and zero server-side configuration.

## New Features

### MCP tools (via `fastapi-mcp`)

- **`scan_api`** — security-scan a single API endpoint in quick or full mode, with bearer/JWT token and cookie authentication.
- **`scan_api_scenario`** — replay an authenticated, ordered API workflow. Steps run in dependency order, capturing and propagating variables, cookies, and tokens between steps before scanning the authenticated endpoints.
- **`scan_api_suite`** — scan an application composed of multiple API services. Each service's OpenAPI spec expands into child `scan_api` operations that fan out in parallel across the worker pool and aggregate into a single application report.
- **`scan_website_application`** and **`scan_interactive_web_session`** — website scanning with ZAP context creation, form-based authentication, and user management.

### Operations and history

- Asynchronous operation lifecycle with explicit status transitions (including QUEUED); submitting a scan returns an operation ID.
- History API to list operations (filterable by type and status) and fetch past scan results.

### Notifications

- In-process event bus routing platform and operation lifecycle events to notification channels.
- Slack adapter with connection checks, channel resolution, and message delivery.
- Platform lifecycle reporter announcing startup, shutdown, and fatal errors.
- Capability-aware progress rendering: throttled status cards delivered as in-place updates or new messages depending on each channel's declared capabilities.

### Reporting

- Aggregated suite reports in Markdown, JSON, and SARIF 2.1.0 with executive summary, scan/severity/category summaries, recommendations, and deduplicated, deterministically ordered findings.
- Scan reports include TLS protocol status (TLS 1.0–1.3) alongside vulnerability findings.

## Platform Architecture

The release establishes a layered, event-driven platform designed so future capabilities reuse the same infrastructure:

- **Operation orchestration** — a strongly typed operation registry with handler and execution-strategy abstractions (worker-bound vs. orchestration). The background dispatcher is fully tool-agnostic; registering a new tool is a single registration line with no dispatcher or worker-service changes.
- **Worker management** — a self-registering worker pool. Workers register over HTTP at startup and heartbeat periodically; management endpoints support listing, draining, and removing workers. Operations orphaned by a dead worker's heartbeat timeout are failed automatically.
- **Persistence** — PostgreSQL and DynamoDB DAO backends behind a common interface, with the persisted operations table doubling as the dispatch queue, plus a SQL migration runner.
- **Notification infrastructure** — hexagonal ports (event publisher, notification channel) with an in-process dispatcher, assembled by a composition root from settings.
- **Layered structure** — routers are thin HTTP adapters delegating to services; integrations (ZAP client, Slack) are isolated behind service boundaries.

## Improvements

- Request-time validation fails fast with actionable HTTP 422 messages: invalid or relative URLs, inconsistent auth configuration, duplicate/unknown/circular scenario dependencies, duplicate suite categories, empty category expansions, and malformed OpenAPI specs are rejected at submit.
- Request schemas carry field descriptions, enum documentation, and per-tool examples, surfaced in the MCP tool catalog and OpenAPI schema.
- Typed, domain-scoped configuration modules with fail-fast validation of required secrets, database, and ZAP settings in production.
- Progress reporting threaded through the ZAP client, dispatcher, and scanner services so notifications reflect real scan phases.
- Docker Compose stack with healthchecks and opt-in hot reload for local development; comprehensive `.env.example`.

## Bug Fixes

- ZAP container entrypoint no longer double-invokes the ZAP binary, which previously caused ZAP to attempt to open its own launcher script as a target file.
- Container shutdown delivers SIGTERM directly to the application server, so lifespan shutdown hooks — including the shutdown notification — run reliably.

## Breaking Changes

- The request field `project_name` was renamed to `report_group` across all ZAP tools, schemas, and reports; the old name is no longer accepted.
- In `scan_api_suite`, `application_name` was renamed to `suite_name`. The old name is still accepted on input as an alias, but the aggregated report key changed from `application_name` to `suite_name` — report consumers must update.
- Some previously invalid requests (e.g., relative target URLs) that used to fail during execution now fail immediately at submit with HTTP 422. Valid requests are unaffected.

## Technical Notes

- Python 3.12, FastAPI, `fastapi-mcp`, Pydantic settings; ZAP driven through the `zaproxy` client.
- Public HTTP surface: MCP tool endpoints, worker management (register/heartbeat/list/drain/remove), scan history retrieval, and liveness/readiness health probes.
- Test suite mirrors the source layout (services, integrations, flows), covering validation, ordering, variable propagation, OpenAPI expansion, orchestration, aggregation, reporting determinism, and notification flows.
- Module-level documentation under `docs/owasp-zap/` (overview and decision tree, per-tool references, migration notes) and a configuration reference under `docs/`.

## Future Direction

This release establishes the technical foundation — operation orchestration, worker management, persistence, notifications, and the extensible tool architecture — on which future MCP Server capabilities will be built.
